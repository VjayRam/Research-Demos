RaBitQ: one bit per dimension, with a distance error you can actually bound

Product Quantization trains a codebook on your data and hopes it generalizes. When it doesn't — the paper's own example is the MSong dataset, where PQ's relative distance error blows past 50% — there's no theory to fall back on, only re-tuning. RaBitQ replaces the trained codebook with a random rotation plus a single sign bit per coordinate, and in exchange gets a provably unbiased distance estimator with a distortion that shrinks as O(1/√D), for every dataset, with no training step at all.

arXiv:2405.12497 · RaBitQ, Gao & Long, SIGMOD 2024

00 · The problem

Product Quantization has no error guarantee

PQ splits a D-dimensional vector into sub-vectors, k-means-clusters each sub-space on the dataset, and stores a per-subvector cluster index. It works well when the data is well-behaved, but there's no bound on how bad the reconstruction error can get for a dataset whose sub-space structure the training pass didn't anticipate. The paper's motivating example:

from the paper On the dataset MSong, PQ with the standard fast SIMD-based implementation incurs more than 50% average relative error on estimated distances — and recall of ANN search never exceeds 60%, even with exact-distance re-ranking applied afterward. Re-ranking can't fix a candidate list that's already missing the true neighbors.

RaBitQ's answer is to give up the trained codebook entirely. It quantizes with a random, data-oblivious transform, and in exchange derives a closed-form, distribution-free bound on how wrong its distance estimate can be — a bound that holds for any input vector, adversarial or not, because randomness (not the data) is doing the work.

01 · Notation

Every vector is first centered and normalized

Raw data and query vectors are written or and qr. RaBitQ is meant to sit inside an IVF index: each data vector belongs to a KMeans cluster with centroid c, and both data and query are recentered on that centroid, then normalized to unit length:

o := (or − c) / ‖or − c‖    # unit vector, same for q

The Euclidean distance between the original raw vectors reduces to the inner product of the two unit vectors, plus two norms that are cheap to keep around:

‖or − qr‖²  =  ‖or−c‖² + ‖qr−c‖² − 2·‖or−c‖·‖qr−c‖·⟨o,q⟩   Eq. 2

Everything from here on is about estimating that one scalar, ⟨o,q⟩, as accurately as possible from a heavily compressed o.

02 · The core trick

A random rotation turns a fixed codebook into a rich one

Define the tiny, fixed sign codebook — every one of the 2D corners of a D-dimensional hypercube, rescaled to unit norm:

𝒞 := { +1/√D, −1/√D }D   Eq. 3

Sample one random orthogonal matrix P (once, shared by every vector in the index) and rotate that entire codebook with it:

𝒞rand := { P·x  |  x ∈ 𝒞 }   Eq. 4

P is a single global draw, not fit to the data — so unlike a PQ codebook, there's nothing to overfit and nothing that can generalize badly. Encoding a data vector o means picking whichever corner of the rotated cube it's closest to:

ō := argmaxx ∈ 𝒞rand ⟨o, x⟩   Eq. 7

Because P is orthogonal, ⟨o, Px⟩ = ⟨P⊤o, x⟩ — so this is exactly the same search as first un-rotating o into o' := P−1o, then finding the nearest corner of the plain codebook 𝒞 to o'. That reduces to one sign per coordinate.

Try it — rotate a worst-case vector, watch the coordinates spread before signing
o (before P−1) o' = P−1o (signed → the bits)

No matter how concentrated o starts — a single spike, even — its rotated image o' spreads mass across every coordinate, so no single dimension dominates the sign pattern. That's what lets the same fixed, data-oblivious 1-bit codebook work uniformly well on any input.

03 · Encoding

The D-bit code, spelled out

Write the bit string as x̄b ∈ {0,1}D, one bit per coordinate of o', then map bits back to ±1/√D:

x̄b[i] := 1[ o'i ≥ 0 ]    # the stored code, D bits total
x̄  :=  (2·x̄b − 1D) / √D   from §3
ō  :=  P·x̄    # the reconstructed unit vector implied by the code

ō is never actually materialized at query time — every downstream computation works with rotation-invariant inner products, so only the D-bit string x̄b per vector plus the shared P ever needs to be stored. That's D bits per vector versus PQ's usual 2D bits (typically 8-bit codes over D/4 sub-quantizers by default).

04 · Why one dot product is enough

The unbiased estimator, and the geometry behind it

The estimator the paper proposes for ⟨o,q⟩ uses nothing but the quantized code and the query:

estimator  :=  ⟨ō, q⟩ / ⟨ō, o⟩

The numerator is one dot product between a 1-bit vector and a query; the denominator, ⟨ō,o⟩, is a scalar that only depends on which corner of the cube got picked relative to the true direction — it can be computed once at index time and stored alongside the code. Decompose the query relative to o: let e1 be the unit vector in the direction of whatever part of q is orthogonal to o. Then, for non-collinear o,q:

⟨ō,q⟩  =  ⟨ō,o⟩·⟨o,q⟩  +  ⟨ō,e1⟩·√(1−⟨o,q⟩²)   Lemma 3.1

Divide both sides by ⟨ō,o⟩ and take expectation over the random draw of P (equivalently, since ō's direction relative to o is rotation-symmetric, over a uniformly random unit vector orthogonal component): e1 is symmetric under sign flip, so E[⟨ō,e1⟩] = 0, and the second term vanishes in expectation — leaving:

E[ ⟨ō,q⟩ / ⟨ō,o⟩ ]  =  ⟨o,q⟩   Eq. 13, unbiased
The Lemma 3.1 decomposition, interactively

Drag the angle between o and q. The component of q along o contributes the signal ⟨ō,o⟩·⟨o,q⟩; the component along e1, orthogonal to o, contributes noise that a fresh random P makes zero-mean — it's this second term whose randomness is responsible for the estimator's variance, not its bias.

05 · How tight is it

Theorem 3.2 — a concentration bound, not just unbiasedness

Unbiasedness alone doesn't tell you how far a single estimate can stray. The paper proves a high-probability bound on the error, in terms of a confidence parameter ε0:

P{ | ⟨ō,q⟩/⟨ō,o⟩ − ⟨o,q⟩ |  >  √((1−⟨ō,o⟩²)/⟨ō,o⟩²) · ε0/√(D−1) }  ≤  2e−c0ε0²   Theorem 3.2

In practice the paper sets ε0 = 1.9, which it describes as "nearly perfect confidence" for the failure probability on the right. The bound depends on D only through 1/√(D−1) — the whole point: distortion shrinks predictably as dimension grows, with no dependence on the data distribution at all.

The one data-dependent quantity left, ⟨ō,o⟩, isn't left to chance either — it concentrates tightly around a known constant:

E[⟨ō,o⟩]  =  √(D/π) · 2Γ(D/2) / ((D−1)·Γ((D−1)/2))   from §3.2

For any realistic D from a hundred to a million, this expectation sits in a narrow band — the paper reports 0.798 to 0.800 — with deviation bounded by Ω(1/√D). In other words: no matter what the data looks like, about 80% of the reconstructed unit vector's length points the right way.

06 · The other half of the dot product

Queries get their own scalar quantizer

Storing the data side at 1 bit/dimension is only half the win — computing ⟨ō,q⟩ still needs q in a cheap form too. RaBitQ scalar-quantizes the (rotated) query q' := P−1q into unsigned Bq-bit integers, coordinate by coordinate, using its own min/max range and randomized rounding (so the rounding error is itself unbiased):

vl := mini q'[i],   vr := maxi q'[i]
Δ  :=  (vr − vl) / (2Bq − 1)
q̄u[i]  :=  ⌊ (q'[i] − vl)/Δ  +  ui ⌋,   ui ∼ Uniform[0,1]
q̄  :=  Δ·q̄u  +  vl·1D

The random offset ui before flooring is what makes the rounding unbiased in expectation, rather than a fixed systematic truncation — the same spirit as dithered quantization anywhere else.

07 · Making it fast

Bit-plane popcount instead of a lookup table

PQ's fast path is a lookup table per sub-quantizer. RaBitQ's fast path is bitwise: split the Bq-bit query code into Bq separate bit planes, AND each plane against the 1-bit data code, popcount the result, and recombine with powers of two:

⟨x̄b, q̄u⟩  =  ∑j=0Bq−1 2j · ⟨x̄b, q̄u(j)⟩,    ⟨x̄b, q̄u(j)⟩ = popcount( x̄b & q̄u(j) )

Every term is a machine-word AND plus a hardware popcount instruction — no multiplication, no gather from a table. The paper reports roughly 3× faster single-query distance computation than PQ on average, while remaining just as SIMD-friendly for batched scans as PQ's own fast implementation.

08 · The whole pipeline

IVF clustering, probing, and confidence-gated re-ranking

RaBitQ isn't used standalone — the paper builds it inside an IVF index. At build time, KMeans clusters the dataset; each vector's own cluster centroid is the c from §01, so every vector is normalized relative to a nearby, cheap-to-compute point rather than the global mean. At query time, the query probes its Nprobe nearest cluster centroids and scans the RaBitQ codes stored in each.

The error bound (§05) is what makes re-ranking cheap rather than a fixed hyperparameter guess. Since Theorem 3.2 gives an explicit confidence interval around every estimated distance, a candidate can be dropped without ever computing its exact distance the moment its lower bound already exceeds the current k-th best exact distance found so far:

from the paper "Due to the theoretical error bound, the re-ranking strategy has the guarantee of correctly sending the true nearest neighbor from the probed clusters to re-ranking with high probability." PQ has no equivalent guarantee — its re-ranking budget is a fixed constant, tuned empirically per dataset.

Reported index-build cost on GIST (1M vectors, 960 dimensions, 32 threads): RaBitQ 117s, versus PQ 105s and OPQ 291s — comparable to PQ despite computing the rotation and the exact-inner-product bookkeeping per vector.

10 · What it buys you

Storage: D bits vs. PQ's 2D bits

RaBitQ's data-side code is exactly D bits per vector, plus a handful of per-vector scalars (‖or−c‖, ⟨ō,o⟩) that cost a few bytes total regardless of D. PQ's default configuration spends 2D bits (one 8-bit code per sub-quantizer, D/4 sub-quantizers by the paper's stated default) — twice the bits for a codebook that, unlike RaBitQ's, can fail arbitrarily badly on the wrong dataset.

Query-side cost is separate and tunable: Bq bits per query coordinate (§06), chosen independently of the 1-bit data code — a knob PQ doesn't have, since PQ quantizes data and query symmetrically through the same codebook.
